Chapter 1

Project Introduction & Objectives

1.1 Project Overview

The Smart Hostel Management System is a full-stack, enterprise-grade web application engineered to modernize and digitize the administration of residential campus hostels. Built using a robust MERN architecture (MongoDB, Express.js, React 19, Node.js) and bundled with Vite 8, the system replaces error-prone manual paper registers and fragmented spreadsheets with a unified, real-time database management platform.

The project addresses four foundational stakeholders within an academic university environment:

  • Students: Can track their physical bed allocation details, submit maintenance grievances with category and priority parameters, monitor repair status updates, and read official hostel notices.
  • Hostel Wardens: Oversee block occupancy, track student allocations, assign maintenance work orders to dedicated technical staff, and manage visitor gate pass check-ins and check-outs.
  • Maintenance Staff: Access an assigned work-order queue, update real-time progress (in_progress → resolved), and provide timestamped resolution notes.
  • System Administrators: Retain global authority over all 14 campus hostels, room capacities, physical bed provisioning, resident status mutations, and real-time database integrity audits.

1.2 Problems Solved by the System

✗ Problems with Traditional Systems
  • Double Bed Allocation: Manual record keeping frequently leads to two students being assigned to the same physical bed.
  • Grievance Black Hole: Maintenance complaints written on paper registers lack SLA tracking, status updates, or technician accountability.
  • Inaccurate Occupancy Data: Administrators lack real-time visibility into vacant bed slots versus broken beds under repair.
  • Security Blind Spots: Campus visitor logs kept in paper books are difficult to audit, search, or reconcile upon exit.
✓ Solutions Delivered by Smart Hostel
  • Partial Unique Database Indexes: Mathematically prevents double active allocations directly at the database engine level.
  • Audited Ticket Lifecycle: Enforces state-machine transitions (pending → assigned → resolved) with technician attribution.
  • Live Aggregation Pipelines: Real-time calculations of vacancy, usable beds, and occupancy percentages across all 14 hostels.
  • Digital Gate Passes: Instant check-in recording with ID proof logging and 1-click check-out timestamping.

1.3 Motivation & Scope

The primary motivation behind this project is to implement genuine database management principles—including referential integrity, compound indexing, transactional consistency, atomicity, and multi-stage aggregation pipelines—within a practical, modern web platform. Rather than building a generic CRUD mock-up, the system was built and tested against the actual campus topology of Indian Institute of Technology Guwahati (IIT Guwahati), modeling all 14 official residential hostels with realistic floor plans, capacities, and resident populations.

Project Architecture & System Design

3.1 System Architecture Overview

The Smart Hostel Management System follows the classic Model-View-Controller-Service (MVCS) pattern. This design pattern strictly decouples HTTP transport logic from business execution and database queries, guaranteeing testability, maintainability, and clean code boundaries.

+----------------------------------------------------------------------------------------------------+ | MVCS ARCHITECTURAL FLOW | +----------------------------------------------------------------------------------------------------+ [User Browser] | | 1. HTTP Request (JSON body, Cookies, CSRF Header) v [Express Router] (/api/v1/...) | | 2. Passes through Global Middlewares (Helmet, CORS, RateLimit, CSRF) v [Route Layer] (e.g. allocation.routes.js) | | 3. Runs Route Middlewares: authenticate() → authorizeRoles("admin", "warden") → validate(schema) v [Controller Layer] (e.g. allocation.controller.js) | | 4. Unpacks req.body / req.params & passes sanitized inputs to Service v [Service Layer] (e.g. allocation.service.js) | | 5. Executes Business Logic, Adaptive Transactions, Pre-conditions v [Model Layer] (e.g. allocation.model.js) | | 6. Interacts with MongoDB Engine (Partial Indexes, Validations, Aggregations) v [MongoDB Database] (hostel_management)

3.2 Request-Response Lifecycle

Every incoming HTTP request traverses a strictly controlled multi-stage security and validation pipeline before reaching business logic:

  1. Security Headers (Helmet): Injects HTTP headers to disable unsafe scripts and iframe embedding.
  2. CORS Verification: Confirms the client origin matches trusted development and production domains (localhost:5173, 127.0.0.1:5173).
  3. Rate Limiting: Enforces an allocation of 3,000 requests per 15 minutes during development (100 in production).
  4. Body & Cookie Parsing: Parses request bodies up to 10KB (mitigating buffer overflow attacks) and extracts signed cookies.
  5. CSRF Mitigation: For all mutating HTTP verbs (POST, PUT, PATCH, DELETE), verifies that X-Requested-With === "XMLHttpRequest".
  6. Authentication Middleware: Extracts accessToken, verifies JWT signature, checks the RevokedToken table, and attaches req.user.
  7. Role Authorization Middleware: Verifies that req.user.role belongs to permitted roles (e.g., authorizeRoles("admin", "warden")).
  8. Zod Schema Validation: Validates payload formats, emitting standard 400 Bad Request messages on failure.
  9. Service Execution: Executes atomic operations within withOptionalTransaction.
  10. Standardized Response / Error Middleware: Emits formatted JSON via sendSuccess() or captures exceptions in error.middleware.js.

5.3 Database Indexing Strategy

Database Constraints & Indexes Implemented in Production
  • Hostel.index({ code: 1 }, { unique: true }): Enforces global hostel code uniqueness.
  • Room.index({ hostel: 1, roomNumber: 1 }, { unique: true }): Prevents duplicate room numbers inside the same hostel block while permitting identical room numbers across different hostels.
  • Bed.index({ room: 1, bedNumber: 1 }, { unique: true }): Ensures distinct bed labels within each room.
  • Allocation.index({ student: 1 }, { unique: true, partialFilterExpression: { status: "active" } }): Zero Double Allocation: A student can possess at most one active bed allocation at any given time.
  • Allocation.index({ bed: 1 }, { unique: true, partialFilterExpression: { status: "active" } }): Zero Double Occupancy: A physical bed can be allocated to at most one student at any given time.
  • RevokedToken.index({ expiresAt: 1 }, { expireAfterSeconds: 0 }): MongoDB TTL Index: Automatically purges expired JWT tokens from the collection without requiring scheduled cron jobs.

Chapter 7

Authentication, Session Management & Security

7.1 Authentication Architecture (Cookie-Driven JWT)

Unlike insecure implementations that store JWTs in browser localStorage (leaving them vulnerable to Cross-Site Scripting / XSS attacks), the Smart Hostel Management System implements HTTP-Only Cookie-based Authentication with an in-database revocation list.

7.2 Authentication Middleware (server/src/middlewares/auth.middleware.js)

The authenticate middleware runs on every protected API route:

server/src/middlewares/auth.middleware.jsjavascript
export const authenticate = asyncHandler(async (req, res, next) => {
    const token = req.cookies?.accessToken;
    if (!token) {
        throw new ApiError(401, "Authentication required. Please login.");
    }

    const payload = verifyAccessToken(token);

    // Check token revocation list (Blacklist check)
    const revoked = await isTokenRevoked(payload.jti);
    if (revoked) {
        throw new ApiError(401, "Session has been revoked. Please login again.");
    }

    const user = await User.findById(payload.sub);
    if (!user || !user.isActive) {
        throw new ApiError(401, "Account is inactive or no longer exists");
    }

    req.user = user.toSafeObject();
    next();
});

7.3 Role-Based Access Control (RBAC) Middleware

The authorizeRoles middleware enforces granular permissions across routes:

server/src/middlewares/role.middleware.jsjavascript
export const authorizeRoles = (...allowedRoles) => {
    return (req, res, next) => {
        if (!req.user) {
            return next(new ApiError(401, "Authentication required"));
        }
        if (!allowedRoles.includes(req.user.role)) {
            return next(new ApiError(403, "You do not have permission to access this resource"));
        }
        next();
    };
};

9.1 Student Allocation & Vacancy Management

Purpose: Assigns students to physical beds in active rooms within their hostel block, enforces vacancy constraints, and prevents double bookings.

server/src/services/allocation.service.jsjavascript
export const allocateStudent = async ({ studentId, hostelId, roomId, bedId, allocatedBy }) => {
    return await withOptionalTransaction(async (session) => {
        await requireAdmin(allocatedBy, session);

        // Precondition validations
        const student = await User.findById(studentId).session(session);
        if (!student || !student.isActive || student.role !== "student") {
            throw new ApiError(409, "Only active student accounts can receive allocations");
        }

        const bed = await Bed.findById(bedId).session(session);
        if (!bed || bed.operationalStatus !== "usable") {
            throw new ApiError(409, "The selected bed is not available for allocation");
        }

        // Create allocation record
        const [allocation] = await Allocation.create([
            { student: studentId, hostel: hostelId, room: roomId, bed: bedId, allocatedBy, status: "active" }
        ], session ? { session } : {});

        return allocation.toSafeObject();
    });
};

Critical Code Analysis & Algorithmic Breakdown

11.1 Partial Unique Index Definition

File: server/src/models/allocation.model.js
Concept: Partial Indexes in MongoDB.

server/src/models/allocation.model.jsjavascript
allocationSchema.index(
    { student: 1 },
    {
        unique: true,
        name: "unique_active_allocation_per_student",
        partialFilterExpression: { status: "active" },
    }
);

Explanation: Normal unique indexes enforce uniqueness across every document in the collection. The partialFilterExpression: { status: "active" } instructs MongoDB to apply the uniqueness constraint only to documents where status is active. Historical documents (where status: "vacated") are completely ignored by the index, allowing a student to have multiple historical allocations while mathematically restricting them to at most one active bed.

11.2 Adaptive MongoDB Transaction Wrapper

File: server/src/utils/transaction.js
Concept: Concurrency & Standalone Resilience.

server/src/utils/transaction.jsjavascript
export const withOptionalTransaction = async (callback) => {
    if (!supportsTransactions()) {
        return await callback(null);
    }

    const session = await mongoose.startSession();
    try {
        let result;
        await session.withTransaction(async () => {
            result = await callback(session);
        });
        return result;
    } catch (error) {
        if (error?.message?.includes("replica set member or mongos")) {
            return await callback(null);
        }
        throw error;
    } finally {
        await session.endSession();
    }
};

Explanation: In MongoDB, multi-document ACID transactions strictly require a Replica Set topology. If code attempts to run session.startTransaction() on a local developer's standalone single-node instance, MongoDB throws an error. This adaptive wrapper inspects the client's topology description at runtime. If running in a cluster, it wraps operations in an ACID transaction session; if running standalone, it executes safely with session = null, ensuring cross-environment portability without code modification.

Chapter 15

Security Architecture, Edge Cases & Limitations

15.1 Implemented Security Mechanisms

  • HttpOnly, SameSite Cookies: JWT access tokens are stored in HTTP-Only cookies, preventing JavaScript access and neutralizing XSS token theft.
  • Cryptographic Salting & Hashing: Passwords hashed with Bcrypt using 12 salt rounds. Plaintext passwords are never logged or persisted.
  • Token Blacklisting with TTL: Logout immediately hashes the JWT jti and records it in revoked_tokens. The database automatically discards expired records.
  • CSRF Mitigation: Requires X-Requested-With: XMLHttpRequest on all state-mutating HTTP methods.
  • Rate Limiting: IP-based request throttling prevents brute-force login attempts.
  • Input Sanitization: Zod schemas strictly parse, validate, and trim all incoming request fields.

15.2 Limitations & Proposed Improvements

  • Current Limitation: Image attachments for maintenance complaints (e.g. photos of broken pipes) are not yet integrated with an S3 object store.
  • Future Scope: Implementation of WebSocket subscriptions (Socket.io) for instant real-time notification alerts when a complaint status changes.
  • Future Scope: Integration of automated biometric or RFID gate scanners directly with the Visitor and Attendance service.
Chapter 16

Viva Voce & Technical Interview Preparation

Comprehensive Technical Questions & In-Depth Answers

DBMS Concept
Q1: Why did you choose MongoDB instead of a relational database like PostgreSQL or MySQL?
Concise Answer: MongoDB provides horizontal scalability, dynamic schema evolution for diverse campus entities, and high-performance native aggregation pipelines.
In-Depth: Hostels, room types, and complaint categories vary across campus blocks. MongoDB's document model represents nested real-world relationships naturally while Mongoose schemas enforce rigorous data validation and relational integrity via ObjectId references. Furthermore, MongoDB's partial indexes and aggregation pipelines ($lookup, $facet) offer relational capability with NoSQL speed.
Concurrency & Indexing
Q2: How does your system mathematically prevent two students from being allocated the same bed?
Concise Answer: Through MongoDB partial unique compound indexes on the allocations collection.
In-Depth: We defined a unique compound index: Allocation.index({ bed: 1 }, { unique: true, partialFilterExpression: { status: "active" } }). If two administrators concurrently submit an allocation request for Bed B1, MongoDB accepts the first write and immediately throws an E11000 Duplicate Key Error on the second, translated to an HTTP 409 Conflict.
Security & Auth
Q3: Why use HTTP-Only cookies instead of storing JWTs in browser localStorage?
Concise Answer: Storing JWTs in localStorage makes them vulnerable to theft via Cross-Site Scripting (XSS).
In-Depth: Any third-party script or injected XSS attack can read localStorage.getItem('token'). With HttpOnly cookies, JavaScript running in the browser cannot read the cookie string. The browser attaches the cookie automatically to requests matching the origin. Combined with CSRF headers, this provides enterprise-level security.
DBMS Integrity
Q4: How does your database handle student checkout/vacation? Do you delete the allocation document?
Concise Answer: No, allocation records are never deleted; they are marked with status: "vacated".
In-Depth: Deleting allocations destroys historical occupancy records and audit trails. When vacating, we update status = "vacated", record vacatedAt = new Date(), and set vacatedBy = req.user.id. Because of our partial unique index, vacating the record frees the student and bed for future allocations while preserving historical reporting.
Transactions
Q5: What was the "Transaction numbers are only allowed on a replica set" error and how did you resolve it?
Concise Answer: MongoDB transactions require a replica set or mongos cluster and crash on standalone instances.
In-Depth: We designed an adaptive wrapper withOptionalTransaction in transaction.js that inspects the connection topology. If connected to a cluster, it runs atomic multi-document transactions. If connected to a standalone development server, it executes operations safely without crashing, falling back to structured rollbacks.
Aggregations
Q6: How do you calculate live hostel occupancy percentage?
Concise Answer: Using Mongoose aggregations that count active allocations and divide by usable beds.
In-Depth: In report.service.js, we query hostels, fetch their rooms, aggregate usable physical beds, and count active allocations where status: "active". The formula (Occupied Beds / Usable Beds) * 100 yields the exact occupancy percentage.
Security & Sessions
Q7: How does logout work if JWT is a stateless token?
Concise Answer: Through a token revocation blacklist with MongoDB TTL auto-expiry.
In-Depth: Each JWT contains a unique jti (UUID). Upon logout, the server hashes the jti using SHA-256 and writes it to revoked_tokens with the token's expiration date. The authenticate middleware checks this collection. Once the token's natural expiration passes, MongoDB's TTL index automatically deletes the document.
RBAC Bug Fix
Q8: Why were Wardens initially unable to see complaints and allocations, and how did you fix it?
Concise Answer: The /api/v1/users route was globally restricted to admin only, causing the warden's client-side Promise.all data fetches to fail with 403 Forbidden.
In-Depth: In user.routes.js, authorizeRoles("admin") was mounted at the router level. When wardens visited Complaints or Allocations, the frontend called /users to populate technician and student dropdowns, triggering a 403 error that blocked the entire page. We updated user.routes.js to allow wardens read access (GET /users) while keeping mutations (role changes, deactivations) admin-only.
